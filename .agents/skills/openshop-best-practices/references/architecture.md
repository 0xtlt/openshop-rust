# Architecture

Use this reference before moving behavior across OpenShop boundaries.

## Repo Map

- `crates/openshop/src/engine`: flow execution, steps, scheduling, retries, aborts, and worker behavior.
- `crates/openshop/src/server`: axum server, Shopify auth, webhooks, app proxy, Admin API routes (`server/api`), functions, MCP (`server/mcp`), the operator dashboard (`server/ops`), crypto, logs, and shop isolation.
- `crates/openshop/src/cli`: commands of an application binary: `dev`, `start`, `worker`, and `migrate`.
- `crates/openshop/src/db`: connection pool, framework row types (`schema.rs`, four of them read-only records: `Installation`, `FlowRun`, `StepResult`, `LogRow`), models (`#[derive(Model)]`, the traits `Record` and `Model`, `Table`), typed rows (`record.rs`), the schema snapshot and its comparison (`diff.rs`), and migrations.
- `crates/openshop/src/admin`: server side of custom admin pages (access rules, loaders, actions).
- `crates/openshop/src/config/validate.rs`: validation of an application definition.
- `crates/openshop/src/runtime`: environment (`RuntimeEnv`), logging, and the outbound HTTP transport.
- `crates/openshop/src/shopify`: Shopify Admin GraphQL client.
- `crates/openshop/src/testing`: test harness, compiled with the `testing` feature.
- `crates/openshop/src/types.rs`: the definitions an application registers (providers, flows, crons, webhooks, proxies, routes, functions, MCP), the contexts of their handlers, and `ShopScope`, the trait of the contexts that belong to a shop. The module is private: each item is exported from the root or from `openshop::builder`.
- `crates/openshop/src/declare.rs`: `App`, the value `app!` declares (`APP.main()`, `APP.config()`), `Declared`, the trait every attribute implements for its block, and what the generated code calls: the `dispatch` of a flow, the typed input of a proxy or a route.
- `crates/openshop/src/template.rs`: `Liquid` and `liquid!`, the Liquid templates of app proxies.
- `crates/openshop/src/app.rs`: `OpenShopConfig`, `OpenShopBuilder` (the lower level `app!` expands to), and the `OpenShop` handle.
- `crates/openshop/src/lib.rs`: the root of the crate, the `prelude` module, and the documentation of every macro. The root exports what an application names (attributes, `app!`, contexts, settings, the values handlers exchange), by an explicit list: add a name to it only when application code writes that name. Everything else is exported from its module (`openshop::engine`, `openshop::server`, `openshop::db`, `openshop::admin`, `openshop::runtime`, `openshop::shopify`).
- `crates/openshop/src/builder.rs`: `openshop::builder`, the lower level in one place: `OpenShopBuilder` and the definitions a block is built from by hand (`Flow`, `Provider`, `Field`, `Proxy`, `Route`, `Webhook`, `Function`, `McpTool`, `McpResource`, `AdminPage`, `Table`, `InputSchema`). Generated code names them by this path.
- `crates/openshop-macros`: `app!`, the attributes and derives of the building blocks (`#[flow]`, `#[webhook]`, `#[proxy]`, `#[route]`, `#[admin_page]`, `#[mcp_tool]`, `#[mcp_resource]`, `#[provider]`, `ProviderConfig`, `FunctionConfig`, `Model`), `#[input]`, `#[openshop::test]`, and `graphql!`. Their documentation is in `crates/openshop/src/lib.rs`.
- `crates/openshop/migrations`: framework schema SQL, embedded in the crate.
- `crates/openshop/ui-dist`: prebuilt admin UI bundle, committed and embedded in the crate.
- `crates/openshop-shared`: types and rules shared by the server and the WebAssembly UI.
- `crates/openshop-ui`: embedded admin UI written with Leptos and Shopify's Polaris web components, compiled to WebAssembly; its own workspace. `openshop` re-exports its library as `openshop::ui` (feature `ui`), for the views of custom admin pages.
- `crates/openshop-cli`: the `openshop` command (`init`, `init-ui`, `dev`, `build`, `build-ui`); `build.rs` embeds the templates of `init` from `templates/`, `templates/ui` holds the page `init-ui` adds; the shell of a bundle is `crates/openshop-ui/index.html`. `src/bundle.rs` writes and builds the admin UI bundle of an application.
- `templates/`: the templates of `openshop init`, crates of the workspace. `templates/shared` holds the files every project gets (a dotfile as `_name`; `# if views` / `# else` / `# end` blocks, as in the `Dockerfile`, are kept or dropped depending on whether the template's `openshop` has the `ui` feature; `rustfmt.toml` matches the repository's); a project gets `src/`, `tests/`, `migrations/`, `README.md`, `shopify.app.toml` and its `Cargo.toml` from its template, and nothing else of it (`examples/` stays). The migrations of a template are committed, and its tests check them: run `cargo run -- migrate generate` in it after a change to the framework schema or its models.
- `templates/minimal`: one provider and one flow, with the built-in admin.
- `templates/custom`: runnable custom app, built for the merchant who runs it, and integration surface: every building block, with the built-in admin open to the merchant; update it when examples or framework usage change. Its custom admin page has a view, so `openshop build-ui` builds it an admin UI bundle of its own, from its `admin` module.
- `templates/public`: runnable public app, installed by many shops: an admin made of its own pages (`builtin_pages: AdminPagesConfig::none()`, a home at `/`), a flow run for every shop, what a page reads of the runs of its shop (`FlowRun::of(&ctx)`), and the operator dashboard for whoever runs it. Update it when what a merchant or an operator sees changes.
- `apps/preview`: what the preview example of the custom or public template runs (`examples/preview-custom.rs`, `examples/preview-public.rs`), to serve it in a browser without a Shopify store.
- `docs/src`: user-facing documentation (mdBook).

## Boundary Rules

- Keep reusable framework behavior in `crates/openshop/src`; keep sample usage in the templates (`templates/minimal`, `templates/custom`, `templates/public`).
- Do not duplicate framework behavior in the templates when it can live in OpenShop.
- If a public API changes, update docs and the templates in the same change.
- Prefer existing config validation in `crates/openshop/src/config/validate.rs` for definition checks. It runs in `OpenShopBuilder::build()` and again when an `OpenShop` is created, and checks the `input` of a cron against the input of its flow. The builder itself refuses a key registered twice (`flows.syncOrders is registered twice`), a method handled twice on a proxy or route path, and two response types on a proxy path.
- Preserve shop/app isolation by `(app_handle, shop)` in server and database behavior.
- Keep secrets in environment-backed config; never put API secrets in TOML examples.
- In framework code, read environment-backed settings from `app.env()` (`RuntimeEnv`). It is captured once at startup so that requests never read process-global state.
- Template files are embedded with `include_str!` in `crates/openshop-cli/src/init.rs`. Add a new template file to its `TEMPLATE` list.
- Framework schema changes are SQL files in `crates/openshop/migrations`, listed in `FRAMEWORK_MIGRATIONS` (`crates/openshop/src/db/migrate.rs`). Keep them idempotent: `dev` and the test harness execute them on every start.

## Shared App Code

- The admin UI bundle of an application is built by `openshop dev` / `openshop build` from the modules that declare a page with a view (`src/admin/`), compiled to WebAssembly on their own, where a page block keeps only its `#[view]`. Nothing marks the rest of the application, and no file of the bundle lives in it. Keep a module of pages free of the rest of the application outside its server functions: declare what a view receives in that module, and import what only a loader or an action needs inside that function.
- Follow the layout of `templates/custom/src`: one module per block under `flows/`, `providers/`, `webhooks/`, `proxy/`, `routes/`, `admin/`, `functions/`, and `models/`, each declaring its block with an attribute on the function or the struct itself, all listed in the single `app!` declaration of `src/lib.rs` (`pub static APP: App = app! { … };`). `src/main.rs` only runs it: `fn main() -> openshop::Result<()> { openshop_template_custom::APP.main() }`.
- Start every module of application code with `use openshop::prelude::*;`: it has `App`, `Cron`, `Result`, `Context`, `Value`, `Uuid`, `Liquid`, the contexts, `ShopScope`, the derives, `McpPermission`, `McpRiskLevel`, `McpConfig`, `ErrorContext`, `RetryPolicy`, `WorkerConfig`, `RunOutcome`, `QueuedRun`, the attributes, `app!`, `graphql!`, `liquid!`, `anyhow!`, `bail!`, `json!`, and the modules `validators` and `response`. Import explicitly only what it lacks: `openshop::testing::TestContext`, `openshop::chrono::{DateTime, Utc}`, `openshop::DispatchOptions`, `serde::{Deserialize, Serialize}`, `std::time::Duration`. It does not have `#[openshop::test]`: write the attribute with its path.
- An application depends on `openshop` and `serde`. Do not add `schemars` (`#[input]` derives the schema) or `tokio` (`APP.main()` starts the runtime; `APP.run().await` is for a binary with its own runtime).
- No function builds a block or the configuration. Write `#[flow("syncOrders")] pub async fn sync_orders(ctx: FlowContext, input: SyncOrdersInput) -> Result<()>`, not `fn sync_orders() -> Flow`; write `app! { flows: [sync_orders] }`, not `fn config()` with `OpenShopConfig::builder()` and `openshop::cli::run(config)`; write `fn main() -> Result<()> { APP.main() }`, not `#[tokio::main]`.
- Nothing is discovered from the file system, and an attribute alone registers nothing. A block exists only once it is listed in `app!`, under the list of its kind: `providers`, `flows`, `functions`, `models`, `admin_pages`, `webhooks`, `proxies`, `routes`, `mcp_tools`, `mcp_resources`. A block listed under another kind, or a function without its attribute, does not compile.
- Every other entry of `app!` is a setting, `name: value`, passed to the `OpenShopBuilder` method of that name: `crons`, `on_error`, `mcp`, `admin_menu`, `shopify`, `worker`, `retry_policy`, `builtin_pages`, `admin_ui`, `max_request_body_bytes`, `ops_password`, `sentry`.
- A function attribute leaves the function an ordinary function and adds a type of the same name, which is what the lists take and what carries the constants (`sync_orders::NAME`, `orders_create::TOPICS`, `reviews::PATH` and `reviews::METHOD`, `status::NAME`, `guide::URI`); a struct carries its own (`Warehouse::NAME`, `Warehouse::PUSH`, `VolumeDiscount::NAME`, `ReviewsPage::PATH`). Do not re-export a declared function next to a module of the same name (`pub use sync_orders::sync_orders;` beside `mod sync_orders;` does not compile); import it where the application is declared. Refer to a block by its constant instead of repeating its name: `Cron::new("0 2 * * *", sync_orders::NAME)`, `ctx.fakes.for_call(Warehouse::PUSH)`.
- Declare each kind of block in its form:
  - Flow: `#[flow("name", timeout = "10m", step_timeout = "30s", concurrency = allow, retry_policy = …)]` on `async fn(ctx: FlowContext) -> Result<()>`, with the input as an optional second argument, a type marked `#[input]`. `concurrency` is `allow` or `reject`. A timeout is text checked at compile time (`"30s"`, `"10m"`, `"1h30m"`; units `ms`, `s`, `m`, `h`, `d`), or a `Duration` expression. Without a name, the flow is named after the function in camel case.
  - Input: `#[input]` on the type a flow, an MCP tool or an admin loader or action receives, above its `#[derive(Debug)]`. It derives `Deserialize`, `Serialize` and `JsonSchema`, and names the fields in camel case outside Rust (`product_id` is `productId`) unless the type has its own `#[serde(rename_all = "…")]`. Constrain a field with `#[schemars(range(min = 1))]` or `#[schemars(length(min = 1))]`.
  - Webhook: `#[webhook("orders/create", …)]` on `async fn(ctx: WebhookContext) -> Result<()>`, with the payload as an optional second argument: a type with `#[derive(Deserialize)]` from `serde`, never `#[input]`, because Shopify names its fields in snake case.
  - App proxy: `#[proxy(GET, "/reviews", liquid)]` on `async fn(ctx: ProxyContext) -> Result<T>` where `T` serializes, one function per method of a path; the response type is `json` (the default), `liquid` or `html`, the same for every method of the path. A `liquid` proxy returns a `Liquid`; an `html` proxy returns a string such as `include_str!("page.html")`.
  - Server route: `#[route(POST, "/orders/:id", json, auth = partner)]` on `async fn(ctx: RouteContext<Partner>) -> Result<T>`, one function per method of a path, each with its own authentication; public without `auth`. The authentication function returns `Result<RouteAuthOutcome<Partner>>`, and what it returns for an authenticated request is `ctx.auth`, a `Partner`: give it a type of its own instead of a `json!` value. A plain `RouteContext` carries a `Value`, `Null` on a public route. With `json`, `T` is anything that serializes; without it, `T` is a response (`response::Response`, `(StatusCode, String)`…).
  - Typed input of a proxy or a route: a second argument whose type implements `Deserialize`, read from the query string for `GET` and `DELETE` (and `HEAD`, `OPTIONS` for a route) and from the JSON body for `POST`, `PUT`, `PATCH`. A request that does not fit is answered `422` with `{ "error": "Invalid input: …" }` before the handler runs. Do not parse `ctx.query` or `ctx.body` by hand when the shape is known.
  - Admin page: `#[admin_page("/reviews", nav = "Reviews")]` on the `impl` block of a type, with `#[access]`, `#[loader]` and `#[action]` on its functions (`authorize = Self::rule` for a rule of their own, an optional `#[input]` type as second argument). Unmarked functions are helpers of the server. Listing the page in `admin_pages` serves it, and `nav` gives it its entry in the admin menu: set `admin_menu` only to order or label the menu by hand. A page at `/` is the home of the admin, in place of the built-in dashboard, without `nav`.
  - View of an admin page: `#[view]` on a `fn() -> impl IntoView` (or `fn(params: RouteParams) -> impl IntoView`) of the same block, written with Leptos and `openshop::ui` (feature `ui`). It calls the loaders and the actions of its page through the constants the block gains, `use_loader(Self::LIST_REVIEWS, || ())`, so they return `Result<Output>` with an `Output` that is `Serialize` and `Deserialize`. Never write the view in another crate, or name a function by a string.
  - MCP: `#[mcp_tool("name", permissions(READ_STATUS), risk = low)]` and `#[mcp_resource("scheme://…", name = "…")]` on `async fn(ctx: McpContext) -> Result<T>`; the description is the documentation comment, and a tool returns anything that serializes. Declare a permission once, as a constant next to what requires it: `pub const READ_STATUS: McpPermission = McpPermission::new("status:read", "Read the status").description("…").group("Status").risk(McpRiskLevel::Low);`. Listing it in `permissions(..)` registers it; `permissions(..)` also takes plain keys. Keep `mcp: McpConfig::new().permission(PERMISSION)` for a permission nothing lists, and turn MCP off, with its admin page, with `mcp: McpConfig::disabled()`.
  - Shopify Function: `#[derive(FunctionConfig)]` with `#[function("name", discount = "handle", …)]` on the struct whose fields, with their `#[field(…)]` options, are the configuration form of an instance.
- The builder remains the lower level, for tests and for blocks built at run time: `OpenShopConfig::builder()` with `.add::<Block>()` for a declared block, `.flow(Flow::new(..))`, `.webhook(topic, Webhook::new(..))`, `.proxy(path, Proxy::json().get(..))`, `.route(path, Route::public().get(..))`, `.function(key, Function::new(..))`, `.admin_page(AdminPage::new(..))`, `.mcp_tool(name, ..)`, `.mcp_resource(uri, ..)`, `.model(..)`, then `.build()`. `APP.builder()?` is the builder of a declaration, to add to, and `APP.config()?` its validated configuration.
- The templates (`templates/minimal`, `templates/custom`, `templates/public`) are the references for the declared forms. Keep them in those forms.
- Keep proxy and server route handlers as thin adapters for auth checks, typed inputs, and response shaping.
- Put reusable business logic and Admin GraphQL operations in ordinary modules whose functions take what they need (`&ShopifyClient`, `&PgPool`, `&Connectors`), so flows, webhooks, and routes can share them.
- Use `ctx.shopify`, `ctx.connectors` and `ctx.db` in every context that belongs to a shop: `FlowContext`, `WebhookContext`, `ProxyContext`, `AdminContext`, `McpContext`, and the `RouteShopContext` that `ctx.for_shop("demo.myshopify.com")` returns in a route (`RouteShopInput::new(domain).shopify_app(handle)` for a multi-app setup). `RouteContext` and `RouteAuthContext` have `ctx.db`. Nothing is read when a context is built: the access token is read at the first Shopify request, the provider configuration at the first provider call.
- Keep `ctx.app.shopify_client(shop, shopify_app)` and `ctx.app.connectors(shop, shopify_app)` for code without a context of that shop. They are not `async` and return no `Result`.
- Queue a run from a handler with the `dispatch` of the flow: `sync_orders::dispatch(&ctx, SyncOrdersInput { limit: 10 }).await?`, or `nightly::dispatch(&ctx).await?` for a flow without input. It queues for the shop and the Shopify app of the context and returns a `QueuedRun`. Keep `ctx.app.dispatch_flow(DispatchOptions::new(name, shop)…)` for a flow only known by name, a delay or a retry policy; `DispatchOptions::for_scope(name, &ctx)` takes the shop and the app of a context.
- Keep Liquid in a file next to its handler, never in a Rust string: `src/proxy/reviews.rs` returns `liquid!("reviews.liquid").assign("app_shop", &ctx.shop)` and `src/proxy/reviews.liquid` reads `{{ app_shop }}`. `liquid!` embeds the file at compile time, with a path relative to the source file. `.assign` is the only way a value of the server reaches a template: it is written as an escaped `{% assign %}` before the file. Never build a template with `format!`.

## Flow And Provider Rules

- Step results must implement `Serialize` and `DeserializeOwned` and round-trip through JSON, because completed step output is persisted and reused on retry.
- Write a step with an async closure: `ctx.step.run("fetch-orders", async || { … })`, and the same for `run_with`. Never write `|| async { … }`.
- Propagate the result of `ctx.step.run(..)` and `ctx.step.sleep(..)` with `?`. Sleeping and cancellation travel as errors (`SleepSignal`, `FlowCanceledError`) that the runner must receive.
- Give every step a name that is stable across deployments and unique within a run.
- A canceled or timed-out step is dropped at its next `.await`. Use `ctx.signal` (a `CancellationToken`) in work that does not yield or that you spawn.
- Log with the message first: `ctx.logger.info("Orders fetched")`, `ctx.logger.info_with("Orders fetched", json!({ "count": orders.len() }))`, and the same for `warn` / `warn_with` and `error` / `error_with`. Do not pass an empty `json!({})`.
- Schedule a flow with `Cron::new("0 2 * * *", sync_orders::NAME).name("…").input(json!({ "limit": 1000 }))`, then `.all_shops()`, `.shop("x.myshopify.com")` or `.shops(["a", "b"])`. Without any of them the cron runs once, for no shop. The `input` must be an input of the flow: the application does not start otherwise.
- Give retry policies and worker settings `Duration`s: `RetryPolicy::new().max_attempts(3).initial_interval(Duration::from_secs(1))`, `WorkerConfig::new().concurrency(5).lease_duration(Duration::from_secs(30))`.
- State the constraints of provider and Function fields in `#[field(…)]`: `url`, `non_empty`, `range(min = …, max = …)`, `length(min = …, max = …)`, either bound alone. Keep `validate = <validator>` for anything else: one of `openshop::validators`, or a validator of your own, which runs after the constraints. `label` is optional: without it a field is labeled after its name (`batch_size` is "Batch size").
- Choose who sees the built-in pages. For an application made for one client, leave them visible. For one whose merchants must only reach its own pages, set `builtin_pages: AdminPagesConfig::none()` and declare the home with `#[admin_page("/")]`: the configuration is rejected without it. Open a page again by naming it, `AdminPagesConfig { providers: Some(AdminPageMode::Visible), ..AdminPagesConfig::none() }`.
- Give the operator the dashboard with `ops_password: std::env::var("OPS_PASSWORD").ok()`: the application reads the secret, the framework reads no variable for it. `/ops` then shows every shop, read-only, behind that password; without one it answers `404`. Never add a write to it, and never show there the access token of a shop or the configuration of a provider.
- Report failures with `sentry: std::env::var("SENTRY_DSN").ok()`: the application reads the DSN, the framework reads no variable for it. Failed runs (a warning while they will be retried, an error at the last attempt), handlers that fail and panics are then reported with their flow or route and their shop; do not forward them to Sentry from `on_error` as well. Name the environment and the release with `SentryConfig::new(dsn).environment(…).release(…)`, and reach the other options of the SDK with `.configure(|options| …)`. To capture something yourself, use `openshop::sentry`, never a `sentry` dependency of your own: another version has a client nothing starts. Error messages and log messages are sent as written, except the URLs in them, which lose their credentials, their query string and what looks like a token in their path; log payloads and request paths are never sent. Keep secrets and personal data out of messages, and drop what a library writes for you with `before_send`.
- Read the framework tables through their records, not SQL: `FlowRun::of(&ctx)` in what a merchant can call, `FlowRun::all_shops(&db)` and `Installation::installed(&db)` only behind an authentication of the operator, `StepResult::of_run` and `LogRow::of_run` after finding the run with `FlowRun::of(&ctx).find(id)`. They have no write.
- Describe an application table with a `#[derive(Model)]` struct that names its table first, `#[model("reviews", index(shop, product_id))]`, listed in the `models` of `app!`, and read and write it through `T::of(&ctx)`: every operation is then limited to the shop of the context. `T::for_shop(&db, shop)` is the same where there is no context, such as a test. Use `all_shops` only for maintenance work, and filter on the app handle yourself when several apps share a table. After changing a model, run `cargo run -- migrate generate`, review the SQL and its warnings, declare renames with `#[model(renamed_from = "…")]`, and commit the migration with `migrations/schema.snapshot.json`. Link two models with `#[model(references(Other), on_delete = "…")]` on the id field and index that field; read the other side with a filter, or with a join written in SQL (`sqlx::query!` checks it at compile time when the project depends on `sqlx` with the `macros` feature and a database is reachable while compiling).
- Write a provider as a struct: `#[derive(ProviderConfig)]` with `#[field(…)]` on its fields for the configuration form, and `#[provider]` on its `impl` block, where every `pub async fn(&self, …) -> Result<…>` is a method of the provider and `self` is the configuration of the shop. The provider is named after the struct with a lowercase initial (`Warehouse` is `warehouse`, also `Warehouse::NAME`); write `#[provider("wms")]` only for another name. Mark the connection check with `#[checker]`, keep helpers private, list the struct in the `providers` of `app!`, and call methods with `Struct::on(&ctx.connectors).method(&args)`: the compiler checks the method, its arguments and its result. In tests, `ctx.fakes.for_call(Struct::METHOD)` is the typed fake of a method. `Provider::new(..)` with `handle`, `typed_method` and `ctx.connectors.call(..)` / `call_as::<T>(..)` remain for providers and calls only known at run time.

## UI Rules

- Match the existing compact admin UI instead of adding marketing-style layouts.
- Use Shopify's Polaris web components (`s-page`, `s-section`, `s-table`, …) where the surrounding UI already uses them.
- Keep Admin API calls routed through the fetch helpers in `crates/openshop-ui/src/fetch.rs`, which attach the session token.
- Put types and rules needed by both the server and the UI in `crates/openshop-shared`.
- After changing `crates/openshop-ui`, rebuild with `trunk build --release` and commit `crates/openshop/ui-dist`. The server embeds that directory, so rebuild the server afterwards.
- Keep the `shopify-api-key` meta tag and the App Bridge script tag of `crates/openshop-ui/index.html` as they are: the server rewrites them when it serves the shell.

## Customer Account Extensions

- Customer Account UI extensions should call OpenShop proxy handlers through `/ext/*` with `Authorization: Bearer <session token>`.
- Extension-backed proxy handlers should trust `ctx.shop`, `ctx.shopify_app`, and `ctx.customer_id`; do not trust customer IDs supplied by query strings or request bodies.
- Use `ctx.shopify` inside extension-backed proxy handlers: it is the client of the shop and of the Shopify app the request was authenticated for, so multi-app installs resolve the correct access token.
- For extension frontend code, keep backend origin handling explicit: Shopify CLI tunnel origin in dev, deployed app origin or extension settings in production.
