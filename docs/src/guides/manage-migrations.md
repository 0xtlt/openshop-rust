# Manage migrations

Use this guide when adding app tables or upgrading OpenShop's framework schema.
Start with a generated app, its `migrations/` directory, and an explicitly
configured `DATABASE_URL` for each environment.

## 1. Include the schema

Migrations are SQL files owned by your project. `openshop init` writes the
framework schema as the first files, followed, with the `custom` and `public`
templates, by the tables of their models:

```txt
migrations/
  20261006143115_openshop_init.sql
  20261006143116_openshop_queue_indexes.sql
  20261006143117_openshop_cron_ticks.sql
  20261006143118_openshop_logs_indexes.sql
  20261006143119_openshop_run_lease.sql
  20261006143120_openshop_drop_flow_runs_status_index.sql
```

Each file starts with a marker line:

```sql
-- openshop:framework 0001_openshop_init
```

Keep that line. `migrate generate` and `migrate check` read it to know which
parts of the framework schema your project already covers. Files are applied in
file-name order and recorded in the `__openshop_migrations` table.

Your own tables are described by structs with `#[derive(Model)]`, which name
their table in `#[model("reviews")]` and are listed in the `models` of `app!`.
`dev` and the test harness create them directly, and
`migrate generate` writes the migrations that create and change them
elsewhere. See the [model reference](../reference/database.md#app-models).

Next to the SQL files, `migrations/schema.snapshot.json` records the models as
of the last generated migration. Commit it with them: the next generation
compares the models with it.

## 2. Generate and review locally

After upgrading OpenShop or changing a model, run outside production mode:

```bash
cargo run -- migrate generate
cargo run -- migrate check
```

`migrate generate` writes one file for each framework schema change that
`migrations/` does not cover yet, and one file with the statements that bring
your tables in line with the models. It prints each path. When nothing is
missing it prints `[openshop] No schema changes, nothing to generate`.
`migrate check` fails while the framework schema or a model change is not
covered; run it in CI.

The file for your models is named `<timestamp>_models.sql`, or after `--name`:

```bash
cargo run -- migrate generate --name=add_reviews
```

For this model:

```rust,ignore
use openshop::chrono::{DateTime, Utc};
use openshop::prelude::*;

#[derive(Debug, Clone, Model)]
#[model("reviews", index(shop, product_id))]
pub struct Review {
    pub id: Uuid,
    pub shop: String,
    pub created_at: DateTime<Utc>,
    pub updated_at: DateTime<Utc>,
    pub product_id: String,
    pub rating: i32,
}
```

`migrations/<timestamp>_add_reviews.sql` contains:

```sql
-- add_reviews
-- Generated by `openshop migrate generate`. Review before applying.

CREATE TABLE IF NOT EXISTS "reviews" (
  "id" uuid PRIMARY KEY DEFAULT gen_random_uuid() NOT NULL,
  "shop" text NOT NULL,
  "created_at" timestamp with time zone DEFAULT now() NOT NULL,
  "updated_at" timestamp with time zone DEFAULT now() NOT NULL,
  "product_id" text NOT NULL,
  "rating" integer NOT NULL
);
CREATE INDEX IF NOT EXISTS "reviews_shop_product_id_idx" ON "reviews" ("shop", "product_id");
```

Change the struct later, for example by adding `pub note: Option<String>` and
`pub author: String`, and the next generation writes only the difference:

```sql
ALTER TABLE "reviews" ADD COLUMN IF NOT EXISTS "note" text;

-- WARNING: fails if reviews already has rows: author is NOT NULL without a default. Give it a default, or add it as nullable and backfill it first.
ALTER TABLE "reviews" ADD COLUMN IF NOT EXISTS "author" text NOT NULL;
```

A statement that can lose data or fail on existing rows comes with such a
warning, which `migrate generate` also prints. A migration that drops a table
or a column, or converts a column to a type that can truncate or round its
values (`bigint` to `integer`, `text` to `varchar(20)`), is not written at all
unless you pass `--allow-destructive`; the error lists those statements. Three
things need your attention:

- **Renames.** A renamed field looks like one column dropped and another
  added, which loses its data. Add `#[model(renamed_from = "old_name")]` to the
  field, or to the struct for its table, before generating. See
  [Renames](../reference/database.md#renames). When the drop is what you want,
  run `cargo run -- migrate generate --allow-destructive`.
- **Warnings.** Edit the file when the generated statement is not the one you
  want: add a default, backfill before `SET NOT NULL`, change the cast of a
  type change, clean up the rows that a new foreign key would refuse.
- **Data.** Moving or transforming rows is never generated. Write it in the
  same file, or in an empty one created with `--name` when nothing else
  changed.

A change that cannot be written automatically, such as the primary key or the
constraints of a column, is left as a line in the file:

```sql
-- TODO: the constraints of reviews.product_id changed from none to `REFERENCES products(id)`. Write the statements by hand.
```

Write the statements below it. Until you say they are written, the snapshot
keeps the previous state of that column, `migrate check` fails, and
`migrate generate` reminds you without writing the line again. When the
migrations do what the models say, run
`cargo run -- migrate generate --manual-done`: it records the models as they
are. The flag covers the changes pending when you run it, not later ones.

Review the new SQL under `migrations/` and commit it, with the snapshot and
the code that needs it. `migrate check` does not decide whether a schema change
is safe for your data.

Do not edit a migration after it has been applied: `migrate` compares checksums
and refuses a modified file. Add a new migration instead.

`dev` pushes the schema for local iteration. It creates missing tables and
adds missing columns and indexes; it does not rename, retype or drop
anything, so those changes need their migration applied with
`cargo run -- migrate` even locally, or a fresh development database. A
successful dev session is not proof that committed migrations can upgrade an
existing database. Test the migration sequence on a separate database with the
previous schema.

## 3. Apply committed SQL during deployment

Inject the target environment's `DATABASE_URL` through your deployment platform,
then run the finite migration job once before starting the new app processes.
With the binary built by the generated `Dockerfile`:

```bash
app migrate
app migrate status
```

From a source checkout, the same commands are `cargo run -- migrate` and
`cargo run -- migrate status`.

Expect `pending: 0`. Migration commands do not load the development `.env` file;
export the URL explicitly when running them manually. Without `DATABASE_URL`
they connect to the local development database
(`postgresql://openshop:openshop@localhost:5432/openshop`).

The apply command reads committed SQL from `./migrations` in the working
directory; it does not generate new files. Each pending file runs in its own
transaction. Include the migration directory in the deployment artifact, as the
generated `Dockerfile` does. Web and worker startup never apply migrations.

## 4. Verify and recover

Start the web and worker services and run a harmless smoke flow. If schema access
fails, check the migration job's database URL and status before restarting again.

Take a database backup before a production schema change. If SQL has already
been applied, an application rollback is safe only when the old code remains
compatible with that schema; use a reviewed forward migration or your database
restore procedure otherwise.

Continue with [Deploy to production](deploy-production.md) or
[Upgrade OpenShop](upgrade.md).
